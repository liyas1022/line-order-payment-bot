# 作品介紹

## 專案定位

這是一個以 LINE 為入口的訂單及付款流程展示。使用者不用離開聊天室，即可切換通道、建立訂單、查詢繳費代碼及操作模擬付款。專案展示外部事件接收、資料持久化、狀態轉換和原生訊息介面的整合。

目前支付端採 Mock Payment Service，保留付款 Callback 與狀態更新的介面，讓流程可以重現及測試。

## 三十秒介紹

> 這個作品是用 Flask、SQLite 和 LINE Messaging API 做的訂單機器人。使用者在 LINE 裡選擇通道、輸入金額，就會收到繳費卡片；付款完成後會收到新的狀態卡片。我特別處理 Webhook 重送、訂單擁有者隔離，以及付款通知失敗後的重試。支付端是模擬服務，重點是展示完整資料流與整合設計。

## 可以實際展示的部分

| 展示步驟 | 可說明的能力 |
| --- | --- |
| `/模式` 與速1／速2／速3 | LINE Postback、Quick Reply、模式持久化 |
| `+300` 建單 | 金額驗證、SQLite 寫入、Flex Message 組裝 |
| 查詢自己的訂單 | 使用者身分與資料隔離 |
| 模擬付款 | 狀態轉換、重複操作的處理 |
| 重送測試事件 | 事件去重與交易邊界 |
| Callback 通知測試 | 外部整合、失敗重試及 retry key |

## 面試可討論的設計

- **為什麼選 LINE？** 使用者可以沿用既有聊天介面；選單、按鈕與卡片讓操作流程有明確回饋。
- **為什麼選 SQLite？** 本機啟動方便，能以真正的資料庫交易展示狀態保存；目前的流量與部署範圍適合這個取捨。
- **為什麼保存事件與回覆？** 網路失敗後，外部平台可能重送事件；先保存處理結果能避免重複建立訂單。
- **付款成功但通知失敗怎麼辦？** 付款資料先提交，再保存及重試通知；兩者有各自的完成狀態。
- **下一步如何擴展？** 可加入背景工作佇列、正式資料庫、通知排程、部署監控，再依實際支付業者規格接入真實金流。

介紹時應區分已實作、已測試與未完成的範圍。此作品未提供真實交易量或效能提升數據，也尚未接入正式支付平台。
